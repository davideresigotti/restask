# Changelog

## Unreleased
- The daemon no longer writes into a note you are still typing in. A line saved in the middle of typing reached the server's daemon within a second or two; it gave the line its ID and filed it in `TODO.md` while the editor went on saving the same file. Each such write left a `TODO.sync-conflict-…` copy on the computer, and a line saved again without the ID it had just been given became a second task (the first was deleted on the task server, the second created). The daemon now leaves a note that changed less than 10 seconds ago alone for as long as it still needs that work — the plugin and `restask settle` do it when you leave the line or save. A note that arrives already settled is synced at once, as before; a note edited in a plain editor is picked up 10 seconds after its last save.
- Requests to the task server have a time limit (10 seconds to connect, 60 for the whole request). A server that accepted a connection and then stopped answering held the daemon until it was restarted; it is now a failed pass, retried like any other.
- A task whose entry on the server could not be read keeps its line. A resource the server still listed, with a body that was not a readable `VTODO` in that one listing, was taken for a task deleted on the server: its line was removed from the note. Such a task is now left alone until its resource reads again.
- A task of `TODO.md` whose text ends in a link to a note (`- [ ] call [[John]]`) is no longer taken for a leftover of the view. On a device that did not have the task's sync state yet — it was typed a moment ago there, or the file sync had brought the notes ahead of the `.restask/` folder — the next save in Neovim removed the line from `TODO.md`, and the daemon then deleted the task. Only a line that ends in the link a view writes for a note's task (`[[Note|Note]]`, `[[Note#Heading|Note]]`) is read as one of the view's.
- Task IDs are short. A new task gets `🆔 a42` instead of `🆔 restask-01m4dvv5rt9ps6czhykvj63q4n`: a letter (or a few) that stands for the device the task was made on, and that device's next number — so two devices never make the same ID, also offline. The token is 30 characters shorter on every line, and a task that fits the window no longer wraps because of an ID you do not see. Each device picks its letter by itself the first time it registers a task (`.restask/devices/` in the vault holds who has which). **Existing tasks are renumbered once**, by the daemon, at its first pass after the update: every line gets a short ID, in the notes and in `TODO.md`. On the task server nothing is created or deleted — each task stays the entry it was and is only marked with its new ID — so other apps (Tasks.org, …) keep their tasks, reminders and descriptions. A vault changes over when its daemon is updated, and not before: until the daemon of a vault has made its first pass with the server, the `restask` command and the plugin keep giving new tasks of that vault long IDs, so they can be updated any time — also for a vault whose daemon stays on an older version. **Update every device of a vault before, or together with, its daemon** (`contrib/update.sh` does: the `restask` command, the plugin, then the server), and reload the plugin in Obsidian on each device: an older `restask` or plugin does not know a short ID, takes the line for a new task and gives it a second ID. `restask done --uid` takes the short form (`a42`).
- In the `TODO.md` view the cursor skips the frontmatter and the headings (the lines that are not yours to edit), as Vim's motions skip folded lines, and the view opens with the cursor on the line under `# TODO`, ready for a new task. Obsidian plugin and Neovim (`lock = false` turns it off there). Clicking a heading still works.
- Neovim: with which-key.nvim, the hint shown after `<leader>` lists restask by name (`t → restask`, then `d` toggle and `a` add). Nothing changes without which-key.
- A mirror line that is still in its view under another task ID is no longer read as a deleted task. An older `restask` settling a vault that a newer one had rendered gave the mirror lines of a root note new IDs; the newer daemon then deleted those tasks from their notes. Mixed versions on one vault remain unsupported: update all devices together.
- A root note shows its folder. In a note with `restask-list-root`, the section under a `TODO` heading is now a view like `TODO.md`: the prioritized tasks of every note in the folder and below, filed by priority together with the root note's own tasks, with a `Done` heading for its own completed ones. Ticking, editing, moving or deleting a line there reaches the task in its note. The rest of the note is not touched, and a root note without a `TODO` heading stays as it is. `TODO.md` is unchanged. **Update every device of a vault together** (the daemon, the `restask` binary and the plugin): an older version reads the lines of such a view as tasks of their own. In an existing root note that already has a `TODO` heading, the first pass files the tasks under it into the priority sections; other text under that heading, and the indentation of subtasks there, is not kept.
- Two names for one calendar no longer make the daemon push and delete its tasks in turns. A calendar at `/homelab/` shown as "Home Lab" answers to both `homelab` and `home-lab`; a vault that used both (a note routed to one, `todo_lists` naming the other) had the calendar's tasks created and deleted on the server at every pass. The name that is the calendar's path is used; the other is reported in the log and not synced.
- `restask setup --join` has a running Obsidian load the plugin that is in the vault. A setup that stopped at the server's daemon and was finished with `--join` left Obsidian without the plugin until it was restarted, and said nothing.
- A repeating task without a date (`🔁 every 2 weeks` and no `📅`/`🛫`) reaches the server. Radicale refused it (`HTTP 400`, "push failed; the next pass retries" at every pass). Its `VTODO` now carries a start date marked as restask's anchor; the line in the note gets no date. Other apps show that date as the task's start.
- `restask setup` tries the task server from the always-on server before it changes the vault. A server URL with a name that only the home network's DNS knows no longer ends in "the daemon could not join the vault … error sending request": the daemon is given the address the name has on the computer setup runs on. A server that cannot be reached from there stops the run at once, with the reason.
- Several vaults on one computer and one server. Each vault has its own machine config (`~/.config/restask/config.toml` for the first, `vaults/<vault folder>/config.toml` for a further one), its own daemon unit and, on the server, its own stack (`restask`, then `restask-<vault folder>`, each with its own container and image). `restask setup` for a second vault no longer stops at "the stack in restask serves another vault", and no longer overwrites the first vault's config. A command loads the config of the vault it is run in.
- First public preparation: contributor docs, security policy, issue and PR templates, release workflow.
